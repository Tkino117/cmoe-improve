# 25 静的な構造化プルーニングを対照として測る — 50%で FLAP に負ける

2026-09-10 / 実装 `src/cmoe/prune/{base,flap,llm_pruner}.py`・
`experiments/27_static_pruning/` /
出力 `result_logs/prune27_{flap,llm_pruner}_{block,mlp}`・
`result_logs/prune27_flap_mlp_calib16`（校正を揃えた版）

**結論。** 活性パラメータを揃えると、**提案手法は LLM-Pruner に両動作点で勝ち、
FLAP には 50% で有意に負ける**。25% の負けは校正量の差（FLAP の既定は8倍）で
ほぼ説明できるが、**50% の負けは校正を揃えても残る**。

## 問い

[report/21](21_ew-rule-baseline.md)・[report/22](22_alloc-baselines.md) で足した
対照は、どれも **MoE 変換のうち配分軸だけを差し替えたもの**だった。比較の相手が
「同じ変換の中の別の配分」しかいないので、「そもそも MoE に組み替えることが、
ただ枝刈りするより良いのか」に答えられない。

ExpertWeaver (arXiv:2602.15521) Table 2 は、まさにその問いで training-free の
静的プルーニング2本（FLAP・LLM-Pruner）を並べている。**同じ顔ぶれをこの基盤に
載せる。** どちらも提案手法ではない。

## 揃うもの・揃わないもの

MoE 変換は**全パラメータを保持したまま実行だけを疎にする**。静的プルーニングは
**重みごと消す**。したがって揃うのは

- トークンあたりの活性パラメータ（＝ FLOPs）… 揃えられる
- メモリ … 揃わない（静的プルーニングの側が小さい）

の2つに分かれる。表に載せる比較軸は前者で、後者は静的プルーニングに有利な差と
して明記する。

## スパース率の数え方が食い違う

この基盤の「25%」は **FFN ニューロンの 25% がトークンごとに不活性**（N=8 / A=6）
という意味である。Llama-2-7B の1ブロックは FFN が `3·d·i` = 135.3M、attention が
`4·d²` = 67.1M なので、ブロック全体で見ると

    (1 − A/N) · 3di / (3di + 4d²) = 0.25 × 0.6684 = **16.71%**

にしかならない。一方 FLAP の `pruning_ratio` は attn+FFN 全体に対する比である
（AL-AM の `compression_weight = 512/3` が、ヘッド1本と FFN ニューロン1本の
パラメータ比 `4·d·128 : 3·d` そのものであることが根拠）。LLM-Pruner の
`pruning_ratio` は刈る層の中でのチャネル比で、既定では層 4〜29 の 26 層しか
刈らないため、名目 25% の実効は `0.25 × 26/32 = 20.31%` である。

**同じ「25%」と書くと対照だけが 1.5 倍削ることになる。** ExpertWeaver Table 2 は
これをやっている。ここでは2つの土俵を両方測る。

| `--scope` | 意味 | 25% のときの実効ブロック削減率 |
|---|---|---|
| `block` | 原典の定義そのまま。EW Table 2 と同じ土俵 | FLAP 25.00% / LLM-Pruner 20.31% |
| `mlp` | FFN だけを刈り、活性パラメータを提案手法に揃える | 両方 16.71%（提案と厳密に一致） |

共通軸は**実効ブロック削減率**で、表はこれで並べる。

## 移送

公式実装をそのまま持ち込むことはできない。FLAP も LLM-Pruner も自前の
`modeling_llama.py` を同梱して古い transformers に固定しており（LLM-Pruner は
さらに同梱の `torch_pruning` に依存する）、このリポジトリの 4.47.1 と共存しない。
移したのは統計と規則だけで、EW-rule・OWL・LExI を式だけ移したのと同じやり方である。

### FLAP（`--metrics WIFV --structure AL-AM`）

4段。(1) 刈る前のモデルの上で層ごとに入力チャネルの平均 `baseline_inp` と
ゆらぎ `fluc_inp` を貯める、(2) `WIFV = fluc × Σ_out W²`（attention 側は2乗）、
(3) 層ごとに標準化してから全層・全構造を1本に並べ、パラメータ数で重み付けした
累積が目標に達する所で切る、(4) 落としたチャネルの平均寄与を出力側の bias に移す。

**原典との違いは1点だけ。** 公式実装の `compression_weight` は
`torch.ones_like(indices)`（int64）に `512.0/3` を代入しており、170.667 が 170 に
切り捨てられる。ここは浮動小数のまま使う。切り捨てのままだと目標スパース率が
0.4% ずれる。

**ゆらぎの式は公式実装に厳密に合わせてある。** 公式の `old_baseline_inp` は
**別名であって複製ではなく**、直後の in-place 更新で新しい平均に変わる。したがって
掛け合わせる2因子は同じもので、実体は「更新後の平均からの偏差の2乗和」である。
公式の `BiasGPT` と同じ入力を与えて `baseline_inp` / `fluc_inp` / WIFV の
**差 0** を確認した（`tests/test_prune.py` に式を固定してある）。

### LLM-Pruner（`--block_wise --pruner_type taylor --taylor param_first`）

群は2つしかないので依存グラフの探索は要らない。

- FFN 群（root = `gate_proj` の出力チャネル j）
  `I[j] = Σ_i |W_gate[j,i]·G_gate[j,i]| + Σ_i |W_up[j,i]·G_up[j,i]| + Σ_o |W_down[o,j]·G_down[o,j]|`
- attention 群（root = `q_proj` の出力チャネル、`consecutive_groups` = head_dim
  なのでヘッド単位に潰れる）
  `I[c] = Σ|W_q·G_q|[c,:] + Σ|W_k·G_k|[c,:] + Σ|W_v·G_v|[c,:] + Σ|W_o·G_o|[:,c]` をヘッド内で総和

勾配は10系列を1バッチにまとめた **1回の backward** から取る（原典と同じ）。
刈る本数も原典の `C − int(C·(1−s))` に合わせてある。

**追加学習（LoRA による recovery tuning）は行わない。** 原典はプルーニング後に
alpaca で LoRA を当てるが、ここが比べているのは training-free の土俵であり、
EW Table 2 も追加学習なしの数字を並べている。原典の設計上この手法は recovery を
前提にしているので、そのぶん不利に出る。**手法の欠陥ではなく土俵の違いである。**

原典は fp32 で勾配を取る（CPU 実行の既定）。ここは基盤に揃えて bf16 のモデルで
backward し、`|w·g|` の総和だけ fp32 で持つ。48GB 1枚で peak 25.1GiB に収まるのが
この形しかないためで、fp32 GPU は 54GB になって載らない。

**校正の量を揃えないのは意図的である。** ソースだけを提案手法に揃え、本数と

**提案手法が最も少ない校正（32k トークン）で戦っている**ことは結果と一緒に書く。

## 結果1: 実効の削減率は設計どおりに出た

3 seed の平均。`mlp` は提案手法（N=8 / A=6 と 8/4）と**厳密に一致**している。

| 構成 | 実効ブロック削減率 | 平均 heads | 平均 intermediate |
|---|--:|--:|--:|
| 提案 25%（N=8 / A=6） | 0.1671 | 32.0 | 11008（全部保持） |
| flap `block` 25% | 0.2500 | 31.5 | 6981 |
| flap `mlp` 25% | 0.1671 | 32.0 | 8256 |
| llm_pruner `block` 25% | 0.2031 | 25.5 | 8772 |
| llm_pruner `mlp` 25% | 0.1671 | 32.0 | 8255 |
| 提案 50%（N=8 / A=4） | 0.3342 | 32.0 | 11008（全部保持） |
| flap `block` 50% | 0.5001 | 18.4 | 5095 |
| flap `mlp` 50% | 0.3342 | 32.0 | 5504 |
| llm_pruner `block` 50% | 0.4062 | 19.0 | 6536 |
| llm_pruner `mlp` 50% | 0.3342 | 32.0 | 5503 |

**FLAP は25%の予算では attention をほとんど刈らない。** 落とすのは平均 0.5 ヘッド
だけで、残りを全部 FFN から取る（FFN ニューロンの36.6%）。AL-AM の大域しきい値が

6.5 ヘッドを落とす。50%まで上げると FLAP も 13.6 ヘッドを落とす。

**`block` の2本は横並びに読めない。** LLM-Pruner は層 4〜29 しか刈らないので
名目 25% の実効は 20.31% にしかならない。以降の主表は `mlp`（実効が揃う土俵）で
読み、`block` は「原典の定義をそのまま使うとこうなる」の記録として残す。

## 結果3: 25% の負けは校正量、50% の負けは校正では説明できない

FLAP の既定校正は 2048本×128 = 262k トークンで、提案手法の 16本×2048 = 32k の
**8倍**である。ソースだけを揃えて量を原典の既定に任せたので、ここを揃え直した
（`--calib-match`。FLAP `mlp` のみ、他は一切変えていない）。

| スパース率 | 構成 | WikiText-2 | `acc` | `gold_nll` | 対提案 `acc` | 対提案 `gold_nll` |
|---|---|--:|--:|--:|--:|--:|
| 25% | 提案 | 7.333 | 0.5855 | 3.929 | — | — |
| 25% | flap 校正262k | 7.055 | 0.6017 | 3.771 | +0.0162* | −0.157* |
| 25% | **flap 校正32k** | 7.250 | 0.5830 | 3.982 | **−0.0024** | **+0.054*** |
| 50% | 提案 | 16.364 | 0.4613 | 7.043 | — | — |
| 50% | flap 校正262k | 11.762 | 0.5013 | 5.874 | +0.0400* | −1.169* |
| 50% | **flap 校正32k** | 13.105 | 0.4844 | 6.179 | **+0.0231*** | **−0.865*** |

**25% は引き分けになる。** `acc` の差は −0.0024 [−0.0071, +0.0021] で0をまたぎ、
`gold_nll` は +0.0535 [+0.0333, +0.0734]* で**提案手法が有意に良い**。PPL だけ
FLAP が 0.083 良い。原典の既定で見えていた FLAP の勝ちは、大半が校正量である。

**50% は校正を揃えても負ける。** `acc` +0.0231 [+0.0180, +0.0283]* が 15/15 の層で
改善、`gold_nll` −0.8646 [−0.899, −0.830]*、PPL も 3.26 良い。

**窓の長さを変えても比較は崩れない。** FLAP の `fluc` は系列ごとの総和を系列数で
割る形なので、窓を 128 → 2048 にすると全チャネルが同じ倍率で大きくなる。層ごとの
標準化がその共通倍率を落とすので、AL-AM のしきい値は窓長に依らない。

## 何が残っているか

50%で負ける要因の候補は2つで、この実験では分けられていない。

1. **bias 補償。** FLAP は落とした入力チャネルの平均寄与を `down_proj` の bias に
   移す。MoE 変換の側に対応物が無い。落とす量が増えるほど効くはずで、50%でだけ
   差が残るのと整合する。**これは MoE 側に移植できる要素であり、対照ではなく
   改善の材料になる。**
2. **層別配分そのもの。** FLAP も層をまたいだ標準化と大域しきい値で刈る本数を
   層ごとに変えており、配分軸では提案手法と同じことを別のやり方でやっている。
   50%の差がこちらなら、「配分を探索で決める」という主張の再検討が要る。

1 を先に測るのが安い（MoE の shared/routed で落ちた側の平均寄与を bias に移すだけ。
`moe/modules.py` の変更で足りる）。1 で差が埋まれば 2 は否定される。

## 注意点

- **メモリは揃っていない。** MoE 変換は全パラメータを保持したまま実行だけを疎に
  するが、静的プルーニングは重みごと消す。揃えたのはトークンあたりの活性
  パラメータ（＝ FLOPs）だけで、この軸では静的プルーニングの側が有利である。
  表に載せるときは必ず併記する。
- **LLM-Pruner に追加学習をさせていない。** 原典は LoRA による recovery を前提に
  しており、training-free の土俵ではそのぶん不利に出る。EW Table 2 も同じ扱いだが、
  「LLM-Pruner に勝った」を手法の優劣として書いてはいけない。
- **FLAP は bias を足すぶんパラメータが増える。** 層あたり `d + d` = 8,192 個で、
  ブロックの 0.004% と微小だが、「パラメータ数を揃えた」と書くなら注釈が要る。
- **`block` の実効削減率が手法間で揃っていない**（FLAP 0.2500 / LLM-Pruner 0.2031）。
  原典の定義をそのまま使った結果であり、ExpertWeaver Table 2 の「25% sparsity」も
  同じ問題を抱えている。この表を横並びで読んではいけない。
- **提案手法の負けは動作点に依存する。** 25%（主表の動作点）では引き分け、50%で
  負ける。ICASSP 原稿は 25% と 50% の両方を載せる予定なので、**50% の行をどう
  書くかは避けられない**。
