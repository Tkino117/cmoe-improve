CMoE 実験基盤の設計計画

CMoE の training-free MoE 化研究を続けるための実験基盤を設計する。 参照: CMoE-ref/ の既存実装・レポート 01〜13・ ルーター差し替え実験の実装計画。 作成日: 2026-08-17

目的

CMoE の training-free MoE 化研究を続けるための実験基盤をつくる。 モデル差異を一箇所に閉じ込めた共通の土台の上で、SA 配分とルーターのアルゴリズムを 単独でも同時でも差し替えて比較でき、データセットや探索手法を足すコストが小さい状態にする。

背景・課題

既存の CMoE-ref/ には、CMoE 公式実装を土台に2つのライブラリ層 (xsearch/: 層別配分探索、routerlab/: ルーター差し替え)と、 14 本・約 7,000 行の実験ドライバ scripts/*.py が積み上がっている。 成果は出ているが、実験を1つ足すたびに 500〜800 行のドライバが1本増える構造になっている。

原因は、差し替えたい対象が独立していないことにある。 モデル・データセット・配分アルゴリズム・ルーターアルゴリズムの4つが各ドライバの中で絡み合い、 carving・診断・PPL 測定・ブートストラップまでドライバごとに抱えている。 1つを変えるには、変えたくない部分ごと書き写すことになる。

本設計の要求は、突き詰めると一点に集約される — 差し替えたいもの(モデル・配分・ルーター・データセット)が、それぞれ独立に差し替えられること。

要件

  • モデルごとの差異は一箇所にまとめて閉じ込める。
  • 異なるモデルでも実験ができる。
  • メインで読むコードは、モデルによる差異を気にしなくてよい。
  • ルーター改善のアルゴリズムと SA 配分のアルゴリズムを、それぞれ単独で適用できるし、同時にも適用できる。
  • SA 配分やルーターは今後「計算量を落とす探索」へ改善していくため、その追加実験を効率よく試せる。
  • 評価データセット・キャリブレーションデータセットを、いろいろなものを効率よく試せる。

差し替え軸と境界

6 つの軸を立て、それぞれ「何を受け取り、何を返し、何をそこに閉じ込めるか」を決める。

軸境界入力出力
1ModelAdapterモデル名/パス層のリスト、正規形の dense FFN、FFN 差し替え操作、seqlen・dtype・tokenizer
2DataSourceデータセット名、seqlen、seed、本数carve / fit / eval のトークン列 + メタ
3CarveMethoddense FFN + carve データの活性統計、NPartition(expert グループ、代表候補)
4RouterMethodRouterBuildContext + fit データnn.Module(ルーター)
5ScoreOracle / AllocationSearch配分候補 / オラクルと予算スコアと消費コスト / 配分ベクトル x[L]
6Evaluator組み上がったモデル + eval splitPPL・NLL 列、ルーター診断値

1. モデル — ModelAdapter

閉じ込めるもの: projection の名前、attention の呼び出し規約 (transformers 4.47 の rotary_emb フォールバック依存など)、層リストへの経路、 massive activation 層のような機種固有の事情。

上位のコードは「層 ℓ の dense FFN」と「そこに MoE を差す」ことしか知らなくてよい。 これが要件の1〜3をまとめて満たす軸である。

2. データ — DataSource → Splits

閉じ込めるもの: データセットごとの取り出し方と、split 同士が重複しないための切り出し規則。 出力にはトークンハッシュ・starts などのメタを含める。

既存の routerlab/data.py がほぼこの形になっている。WikiText-2 固定である点を一般化する。

3. 分割 — CarveMethod

閉じ込めるもの: 活性頻度による shared/routed の判定、共活性によるクラスタリング。

出力する Partition には x に依存しない部分だけを持たせる。 現状の実装は x を変えると分割ごと動くため、配分とルーターを独立に扱うには、 ここで x 非依存部分を切り離すことが前提になる。

4. ルーター — RouterMethod

入力の RouterBuildContext では分割・x・Top-K が固定されており、メソッドはそれらに触れない。 出力の nn.Module は、dim と topk が context と一致することを境界側で検査する。

既存の routerlab/contracts.py がそのまま使える。8 方式が実装済み。

5. 配分 — AllocationSearch + ScoreOracle(2 枚に割る)

  • ScoreOracle: 配分候補を受け取り、スコアと消費コストを返す。 実装は L(層ローカル・激安)、suffix KL、実 PPL(高価)と段階を持つ。
  • AllocationSearch: オラクルと予算を受け取り、配分ベクトル x[L] を返す。 greedy / beam / 今後の安価な探索がここに並ぶ。

この 2 枚割りが、「計算量を落とす探索」の実験点になる。 探索アルゴリズムと、それがどのオラクルを何回叩いたかを、同じ土俵で比較できる。

6. 評価 — Evaluator

PPL / NLL を、seed ごとの対応比較とブートストラップができる粒度で返す。 ルーター診断(|h| 回収率、Oracle との一致率)も同じ境界が担う。

組み立て役

Adapter × Data × Carve × Allocation × Router → Model を実行し、Evaluator に渡す。

配分だけ・ルーターだけ・両方は、軸 4 と 5 に「何もしない既定」を入れるだけで表現できる。 report/13 の 2×2 表がそのまま 1 本のドライバから出る形になる。

registry を置くのは差し替え軸だけ

adapters / data / carve / router と、 alloc の search・oracle に registry.py を置く。 CLI は文字列を受けて registry で解決するだけとし、if method == ... を一切持たない。 既存の routerlab/registry.py の方式を横展開する。

experiments/ が scripts/ を置き換える

現行の 700 行ドライバが肥大している原因は、carving・診断・PPL 測定・ブートストラップを各自が抱えている点にある。 それらはすべて assemble.py と eval/ に入る。 実験ファイルに残るのは「どの軸に何を挿すか」と「何を比較するか」だけで、数十行に収まる。 report/13 の 2×2 表は alloc ∈ {uniform3, beam} × router ∈ {cmoe, oracle_recovery} のループ 1 つで出る。

alloc の 2 枚割りが探索コスト実験の要

alloc/oracles/ と alloc/search/ を別ディレクトリにする。 オラクルは「候補 → (スコア, 消費コスト)」だけを返し、探索はオラクルの中身を知らない。 新しい安価オラクルも、新しい探索アルゴリズムも、片方だけを足せる。

依存の向き

moe ← adapters ← carve ← {router, alloc} ← assemble ← eval ← cli/experiments

一方向に保ち、逆流させない。router と alloc は互いを import しない。 両方を同時に使う知識は assemble.py にだけ置く。

third_party/cmoe-ref は import しない

現状の routerlab → xsearch のような依存を残すと、元実装の制約がそのまま新基盤に染み出す。 移すべきロジックは src/cmoe/ 側へ書き直し、元実装は数値比較の参照元としてのみ保持する。
